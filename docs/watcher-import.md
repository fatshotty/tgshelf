# Live Watcher And Master-Channel Import

This guide describes the current implementation in `bot/watcher.py`,
`commands/import_channel.py`, and `FileSystem.import_message`. Live cataloging
and manual history import are implemented. Incremental folder/channel import is
still planned and is not part of the current CLI.

## Setup And Lifecycle

```yaml
telegram:
  upload:
    channel: -1001234567890
  main_bot:
    api_id: 123456
    api_hash: "YOUR_API_HASH"
    bot_token: "YOUR_DEDICATED_BOT_TOKEN"
```

Use a dedicated bot outside `telegram.users`, add it as an administrator of the
master channel manually, and provide at least one usable user-account session
with access to that channel. The watcher performs no automatic join, promotion,
or startup permission check. A successful listening log confirms handler setup,
not end-to-end access validation.

Omitting `main_bot`, setting it to `null`, or using an empty mapping disables the
watcher. A populated mapping requires all three fields shown above. There is no
separate watcher channel setting: `telegram.upload.channel` is always the source,
and `/` is always the logical destination.

Start the watcher with:

```sh
tgshelf --config config.yaml serve
```

The dedicated Telethon client uses `receive_updates=True` and authenticates with
the bot token and an ephemeral `StringSession`. It does not load or save a session
through `session_storage`, does not require its own `accounts setup` entry, and
does not join the download pools. Pool clients use `receive_updates=False`.

`serve` passes the first user client as an initial gateway and supplies the shared
`AccessAdmission` service. The facade's `@managed("import")` wrapper then selects
and leases an authorized user account for each live import, replacing that
initial gateway with the admitted account's gateway. Import requires read access
to the destination folder's effective channel and consumes one shared
`operations.concurrent` slot. Root/master logical access is fixed; real Telegram
access must still work. Import does not retry the whole message with another
account on access denial. Normal shutdown disconnects the watcher and cancels
its health monitor.

## Live Event Flow

The handler subscribes to `events.NewMessage(chats=master)`. It does not inspect
the forwarding header or sender: supported direct posts and forwards follow the
same path, including messages generated by tgshelf itself.

For each message carrying media, the handler opens its own DB session, constructs
a `FileSystem`, and calls:

```python
await fs.import_message(master, message.id, parent_id=ROOT_ID)
```

The user gateway fetches the message again and extracts its document metadata.
Only media exposed as `message.document` are currently supported, including
video/audio sent in that representation. Native Telegram photos and other media
without a document are skipped; text-only messages are ignored by the prefilter.

There are no handlers for message edits or deletions. Changes made later in
Telegram do not automatically rename, update, or delete catalog entries.

## Catalog Representation

A newly cataloged document becomes one `ACTIVE` file in `/` with one Telegram
part at index `0`. The node stores a generated stable ID, name, MIME, total size,
and channel ID. The part stores channel ID, message ID, document ID, size, and
original filename. Node timestamps use database defaults at import time rather
than the original Telegram message date.

The watcher and CLI do not override metadata: the name comes from the Telegram
document, falling back to `file_<message_id>`, and MIME comes from the document,
falling back to `application/octet-stream`.

Import records the existing payload reference without downloading, uploading,
copying, or deleting Telegram content. Small imported documents stay backed by
Telegram; `telegram.upload.min_size` does not convert them to DB-inline files.
Captions are neither parsed nor rewritten by import. Paths, existing node IDs,
multipart relationships, and album grouping are not reconstructed.

## Duplicate References And Name Collisions

The shared `FileSystem.import_message` rules run in this order:

1. If any node already owns `(channel_id, message_id)`, return that node without
   changes. This lookup includes soft-deleted nodes, so scanning the same message
   does not restore a soft-deleted file or move an existing file back into root.
2. Resolve the document; return `None` when no supported document is available.
3. Look up a same-name sibling in the destination, ignoring case. If the returned
   sibling is `ACTIVE`, return it without recording the incoming message. There
   is no content comparison, overwrite, or automatic suffix for the new name.
4. If the returned sibling is `DELETED`, clear its recorded parts, attach the new
   document as part `0`, update channel/MIME/size, and reactivate it. Its ID is
   retained. This replaces DB references without deleting the old Telegram data.
5. Otherwise, create a node and its part, then commit.

The name lookup is not restricted to files or ordered by state. An active folder
with the same name can also suppress an import. Multiple same-name deleted/TEMP
siblings can make the selected sibling ambiguous; there is no explicit priority
between them in this lookup.

Deduplication is an application-level pre-check, not a concurrent-import lock.
The `(channel_id, message_id)` index is not unique. Concurrent watcher/CLI or
multi-instance imports can race; active sibling name uniqueness can reject an
insert, but there is no dedicated retry/reconciliation for that race.

`FileSystem` supports `after_file_import` when a plugin manager is supplied.
Neither the watcher nor the current CLI passes one, so configured plugins do not
run for these imports. See [Plugin Hooks](plugins.md).

## Failure Handling And Recovery

The watcher is best-effort:

- No `main_bot` configuration: silent no-op.
- No user gateway: warning and watcher disabled. Separately, the normal `serve`
  runtime requires at least one usable user account to build its pools.
- Bot startup failure: `[watch]` error plus a notifier call; `serve` continues.
- Unexpected terminal disconnection: the health monitor logs and notifies while
  `serve` stays up. It does not recreate the watcher.
- Individual import failure: `[watch]` exception log; other events can continue.
  There is no per-message alert, persistent retry queue, or scan checkpoint.

Notifier calls always produce local `[notify]` logs. Telegram alert delivery uses
`telegram.notify.bot_token` through the Bot HTTP API, independently of the watcher.
An empty token means log-only delivery; an empty notify channel defaults to the
master. `serve` starts its background queue, and send failures remain best-effort.
Text alerts in the master channel are ignored by the file-message prefilter.

There is no startup history scan or automatic application-level reconciliation
of messages posted during downtime. Use the manual command below to fill gaps.
The files remain in Telegram even if they have not yet been cataloged.

## Manual History Import

```sh
# Scan all master-channel history into root.
tgshelf --config config.yaml import-channel

# Scan only the latest 1000 channel messages.
tgshelf --config config.yaml import-channel --limit 1000
```

This command does not require `main_bot`. It starts configured clients, builds
the runtime, and enters one admission context requiring master-channel read
access. It reads history through the admitted user's underlying Telethon client
and resolves documents through the same account-bound gateway. That user lease
and one shared operation slot are held for the whole scan, and the facade reuses
the existing context for individual imports. Bots do not supply history.
It scans newest first
using `iter_messages(master, limit=...)`; the default `0` means the whole history.
A positive limit counts all inspected messages, including text and unsupported
media, rather than only imported documents.

The command reuses one DB session and commits each new/reactivated file through
`import_message`. It has no persisted progress, destination argument, MIME or
extension filters, or `--rescan` option. A scan/import exception stops the command;
previously committed files remain cataloged and later runs re-check references.
Neither entry point uses `FsExecutor` fan-out. History and document reads have no
explicit proactive request pacing through `operations.actions/within`; the shared
operation budget controls admitted work rather than individual history requests.

The summary prints `imported` and `skipped` with these current semantics:

- Text-only messages do not increment either counter.
- Known message references and media without a supported document increment
  `skipped`.
- A non-`None` import result increments `imported`, even if it is an active
  same-name node and no new message reference was saved.

The live handler likewise logs `cataloged` for a non-`None` result, including an
existing node returned by reference/name. These messages are not proof that a
new node was inserted. Use `[watch]`, `[import]`, and `[notify]` to inspect the
flow.

## Planned Follow-Ups

Automatic downtime reconciliation, stronger concurrent-import coordination,
message edit/delete synchronization, broader media support, and plugin-manager
wiring are not implemented here.

Incremental history import into mapped folders with include/exclude filters,
persistent checkpoints, and controlled history-request pacing is not implemented.
The local `2026-10-21-channel-import` spec/plan describes that extension rather
than the current command's contract. Channel access policy and shared operation
admission are already implemented on `develop`, as described above.
